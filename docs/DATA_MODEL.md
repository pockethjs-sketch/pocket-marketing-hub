# 데이터 모델

## 핵심 원칙

1. 고객사명·프로젝트명 같은 표시값으로 관계를 연결하지 않고 불변 ID로 연결한다.
2. 한 셀에 프로젝트 전체 JSON을 저장하지 않는다.
3. 웹 입력은 대상 탭의 한 행으로 저장하고 `15_활동로그`에 같은 작업의 이벤트를 추가한다.
4. 삭제는 행 삭제가 아니라 `archived_at`을 기록하는 보관 방식으로 처리한다.
5. 고객 화면은 `client_id`, `project_id`, `visibility_code`, 권한 정보를 서버에서 검사한 결과만 반환한다.
6. 사용자·콘텐츠·성과·승인은 서로 독립된 원장으로 관리한다.

## 현재 초기 데이터

- 활성 고객사 2개: UND, 무극
- 활성 프로젝트 2개: UND 90일 프로젝트, 무극 통합 마케팅 운영
- UND 채널 10개
- UND 실행 업무 144개
  - 단계: P0 57개 / M1 31개 / M2 28개 / M3 28개
  - 분야: 마케팅 79개 / 디자인 35개 / 영상 30개
  - 프로젝트 기간: 2026-08-25~2026-12-15
  - `description`, `planned_start_date`, `due_date`: 144개 모두 명시 저장
  - 승인 계획 주석이 있는 `remarks`: 47개; 사용자 미입력 `progress_percent`: 0 유지
- UND 업무 템플릿 144개
- KPI 정의는 프로젝트별로 `11_KPI정의`에 생성하며 목표·단위·측정주기·채널·고객 공개 여부를 독립 관리
- UND 클라이언트 공유 실행계획 승인본 1개 / 섹션 10개
- UND 내부 실행계획은 운영 원장에 설치했습니다. 본문 10개는 `PROJECT_TEAM`, 실행팀 부록 11개는 `POCKET_ONLY`로 분리하며, 공유용 10개와 합쳐 계획 2행·섹션 31행을 유지합니다.
- 참조 HTML 3개
- 데모 고객사·프로젝트 없음. 현재 활성 운영 범위는 UND와 무극 프로젝트이다. 무극은 공개 Google Sheet의 `무극 캠페인 일정표`를 원천으로 프로젝트 기간 2026-08-10~09-09와 업무 20건을 `06_업무`에 저장한다. 2026-08-31 동기화 기준 완료 5건은 `DONE`, 나머지 15건은 `IN_PROGRESS`이며 시작일·종료일 누락은 없다. 원본의 `진행률`은 오늘 기준 일정 경과율이어서 실제 작업 진척으로 이관하지 않으며, 웹에서 사용자가 직접 입력한 진행률만 `progress_percent`에 저장한다. 채널 세팅·계정 구축·아트워크·블로그 세팅 4건은 `P0`, 콘텐츠 제작·포스팅·운영·인터렉션 16건은 `M1`로 분류한다.

## UND 90일 업무 구조

`06_업무`의 UND 144개 업무와 `91_업무템플릿`은 같은 승인 계획을 기준으로 동기화합니다. 일회성 마이그레이션은 기존 103개 업무의 상태·담당자·메모·행 버전을 유지하면서 승인 계획의 의미상 동일 업무를 연결하고, 누락 업무만 추가하는 방식입니다.

팀 트래커 전용 필드는 다음과 같습니다.

| 필드 | 저장 위치 | 의미 |
|---|---|---|
| `plan_week` | 06_업무, 91_업무템플릿 | 해당 단계 안에서 계획된 주차. 명시적인 `due_date`가 없을 때 프로젝트 `start_date`와 단계 일정으로 마감일을 계산하는 기준 |
| `plan_note` | 06_업무, 91_업무템플릿 | 계약·검수·선행조건 등 승인 계획의 원문 주석. 내부·프로젝트팀 상세에만 제공 |
| `contract_linked` | API 파생값 | `plan_note` 존재 여부로 계산하는 Boolean. 별도 시트 열로 중복 저장하지 않으며 고객 응답에는 사유 원문 없이 여부만 제공 |
| `progress_percent` | 06_업무 | 0~100 사용자 직접 입력 진행률. 신규 기본값은 상태와 관계없이 0이며 상태 변경으로 자동 수정하지 않음 |
| `completion_url` | 06_업무 | HTTPS 결과물·완료 링크 |
| `remarks` | 06_업무 | 일정 이슈와 참고사항 |

UND 운영 업무는 P0/M1/M2/M3 단계와 `plan_week`를 기준으로 `planned_start_date`와 `due_date`를 원장에 명시적으로 저장합니다. 날짜가 없는 구버전 행만 화면에서 프로젝트 착수일과 단계·주차를 기준으로 계산합니다.

업무 `일정표` 화면은 `업무 / 세부내용 / 시작일 / 종료일 / 기간(일) / 진행률 / 상태 / 완료링크 / 비고` 9개 열과 일 단위 캘린더를 같은 행으로 연결합니다. 각 업무의 시작일~종료일은 오른쪽 날짜 셀에 색으로 채워지고, 월·일·요일과 오늘 기준선을 함께 표시합니다. 기간은 시작일·종료일을 포함해 화면에서 계산하고 별도 중복 필드로 저장하지 않습니다. Apps Script는 Sheets Date 객체를 KST `yyyy-MM-dd`로 정규화해 브라우저 시간대에 따른 하루 밀림을 방지합니다.

일정표 필터는 별도 저장값을 만들지 않고 `06_업무`의 원천 필드로만 계산합니다. 상태는 `status_code`를 `완료 / 진행 / 보류`로 묶고, 업무 카테고리는 `workstream_code`의 `마케팅 / 디자인 / 영상`을 사용합니다. 업무 일정은 월요일~일요일을 한 주로 하여 `지난주 / 이번주 / 다음주`와 업무의 `planned_start_date`~`due_date`가 하루라도 겹치면 표시합니다. 진행률은 필터 판정에 사용하지 않습니다.

일정표 상단의 `완료 / 진행 / 보류` 집계도 같은 상태 필터를 조작합니다. 선택한 상태를 다시 누르면 전체 상태로 돌아가며, 아래 상태 필터와 선택값을 공유합니다. 집계 숫자는 현재 카테고리·일정 범위 안의 상태별 건수를 유지해 다른 상태로 바로 전환할 수 있게 합니다.

일정표의 기본 행 순서는 `planned_start_date` 오름차순, 같은 시작일이면 `due_date` 오름차순입니다. 두 날짜가 같으면 기존 `sort_order`를 보조 기준으로 사용하고, 시작일이 없는 업무는 마지막에 둡니다. 이 화면 정렬은 `06_업무.sort_order`를 수정하지 않으며 업무 목록의 승인 순서에도 영향을 주지 않습니다.

일정표의 달력 구간 블록은 쓰기 권한이 있는 계정에서 수정 진입점으로 동작합니다. 블록을 한 번 클릭하면 블록 안에 `수정` 버튼이 나타나고, 이를 누르면 수정 모달이 열립니다. 수정 모달은 업무 목록과 동일한 UPDATE API를 사용하며, 저장된 값은 `06_업무`와 `15_활동로그`에 함께 반영합니다. 읽기 전용 고객 계정에는 수정 진입점을 노출하지 않습니다.

일정표 헤더의 `업무 추가`는 업무 목록의 생성 폼과 동일한 CREATE API를 사용합니다. 생성 UI 위치만 일정표 안으로 옮기며 신규 업무의 저장 구조와 권한 검사는 변경하지 않습니다.

## 프로젝트 공통 화면 원칙

프로젝트마다 바뀌는 값은 고객사명, 프로젝트명, 업무·일정·성과 데이터와 공개 범위뿐입니다. 업무 목록, 일정표, 필터, 업무 추가·수정, 로그 같은 화면 프레임과 조작 위치는 프로젝트 ID나 고객사명으로 분기하지 않습니다. 포켓·NS 내부 계정에는 접근 가능한 모든 프로젝트에서 같은 업무 조작 프레임을 제공하고, 각 저장 요청의 실제 쓰기 권한은 Apps Script가 `04_프로젝트권한`을 다시 조회해 최종 검증합니다.

업무 담당 코드 `CLIENT`의 표시명은 고정 문자열이 아닙니다. 현재 프로젝트의 `client_name`을 bootstrap 프로젝트 셸에서 전달해 UND에서는 `UND`, 무극에서는 `무극`으로 표시합니다. 화면별 API 응답의 축약된 프로젝트 정보는 bootstrap 셸과 병합하며, 프로젝트를 바꿔도 고객사명과 권한·페이지 정보가 사라지지 않게 유지합니다.

프런트의 bootstrap 세션 캐시는 권한·프로젝트 셸 계약이 바뀔 때 버전을 올립니다. 캐시가 남아 있더라도 포켓·NS의 업무 프레임 노출은 프로젝트별 캐시 권한값에 의존하지 않으며, 고객 계정은 계속 읽기 전용입니다.

업무 탭의 `업무 로그`는 사람이 판독할 수 있는 운영 이력만 표시합니다. 현재 `06_업무`와 `entity_id`를 대조해 업무명을 복원하며, 업무명 복원이 불가능한 행, 시스템·마이그레이션 행위자, 사용자 필드 변경이 없는 `UPDATED` 행은 제외합니다. 내부 ID, 시스템성 이벤트와 원본 감사 정보는 삭제하지 않고 `세부 로그`에서 유지합니다. 업무 로그에 표시하는 변경 필드는 제목·상태·세부내용·시작일·종료일·진행률·완료링크·비고·우선순위·담당·분야·단계·공개범위로 제한합니다.

## 데일리 회의록

`19_데일리회의록`은 프로젝트별 일일 회의 기록을 한 행씩 저장합니다. `meeting_date`, `title`, `attendees_text`, `discussion_text`, `decisions_text`, `action_items_text`, `created_by_user_id`, `visibility_code`를 분리하며 수정은 `row_version`, 생성·수정은 `15_활동로그` PREPARE/COMMIT으로 추적합니다. 기본 공개 범위는 `PROJECT_TEAM`이고 포켓 운영자만 고객 공개 또는 포켓 전용으로 변경할 수 있습니다.

## 콘텐츠 발행 집계

업무 화면의 콘텐츠 발행 실적은 수동 카운터나 업무 JSON에 저장하지 않습니다. `08_콘텐츠`에서 다음 조건을 만족하는 행만 업무의 `task_id → phase_code` 관계로 집계합니다.

- `status_code = PUBLISHED`
- 롱폼: `LONG_FORM`, `LONGFORM`, `YOUTUBE_LONG`
- 숏폼: `SHORT_FORM`, `SHORTFORM`, `YOUTUBE_SHORT`, `REELS`
- 인스타그램: `INSTAGRAM`, `FEED`, `INSTAGRAM_FEED`, `CARD_NEWS`
- 네이버 블로그: `NAVER_BLOG`, `BLOG`, `ARTICLE`

단계별 목표는 P0 `2/10/10/10`, M1~M3 각각 `2/10/10/4` 순서로 롱폼/숏폼/인스타그램/블로그를 사용합니다. API는 원천을 `08_콘텐츠:PUBLISHED`로 명시하고 실제값과 목표값을 함께 반환합니다.

## 고객 읽기 전용 경계

공개 미리보기와 고객 계정은 `CLIENT_VIEWER + READ_ONLY`로 고정합니다. 고객은 `visibility_code = CLIENT`인 업무만 조회하며 업무 생성·상태 변경·담당자 변경·메모 저장을 할 수 없습니다.

고객 업무 응답에는 일정, 단계, 분야, 분류, 공개 상태, 세부내용 `description`, `plan_week`, 공개 진행 메모와 `contract_linked` 여부를 포함할 수 있습니다. `plan_note`, 내부 담당자 ID, 검토 조직, 차단 사유와 원천 코드는 제외합니다. 계약 연계 여부가 `true`여도 계약·검수 사유 원문은 노출하지 않습니다.

## 클라이언트 공유 실행계획

`17_실행계획`은 승인본의 버전·기간·목표를 저장하고 `18_실행계획섹션`은 실행 개요부터 미팅 결정사항까지 10개 섹션을 순서대로 저장합니다. 원본 HTML의 스크립트·스타일·SVG 장식은 저장 전에 제거하며, 서버와 브라우저가 본문 HTML을 각각 다시 정제합니다. 공개 행은 `visibility_code = CLIENT`, `source_code = CLIENT_APPROVED_PLAN`, `status_code = PUBLISHED`만 사용합니다. 실행계획은 읽기 전용이며 실제 진행률은 `06_업무`, 발행 실적은 `08_콘텐츠`에서 별도로 계산합니다.

## 내부 실행계획

내부 실행계획도 별도 JSON 셀이나 새 탭을 만들지 않고 `17_실행계획` / `18_실행계획섹션`에 같은 정규화 구조로 저장합니다. 계획 종류는 기존 `source_code`로 구분합니다.

| 계획 종류 | source_code | 계획 공개 범위 | 섹션 공개 범위 |
|---|---|---|---|
| 클라이언트 공유용 | `CLIENT_APPROVED_PLAN` | `CLIENT` | `CLIENT` |
| 내부 실행계획 | `INTERNAL_EXECUTION_PLAN` | `PROJECT_TEAM` | 본문 `PROJECT_TEAM`, 실행팀 부록 `POCKET_ONLY` |

내부 원문을 Git에 커밋하지 않습니다. `scripts/generate-und-internal-plan.mjs`가 로컬 원문을 정제해 gitignored 임시 Apps Script 번들을 만들고, 관리자 마이그레이션으로 원장에 안정적인 ID를 upsert한 뒤 임시 번들은 배포 소스에서 제거했습니다. 고객 역할은 내부 계획을 요청할 수 없고 내부 계획 행 자체도 `mhCanSeeRow_` 공개 범위 검사를 거칩니다.

## 고객사 계정·페이지 권한

- `03_사용자`: 고객 계정 ID를 내부 `@hub.local` 식별자로 정규화하고 표시 이름, `CLIENT_VIEWER`, 활성 상태를 저장합니다.
- `04_프로젝트권한`: 계정과 고객사·프로젝트 연결, `READ_ONLY`, `allowed_pages_json`을 저장합니다. 현재 선택 가능한 허용 페이지 코드는 `overview`, `plan`, `tasks`, `daily`, `performance`, `files`입니다. `tasks`는 같은 원천을 쓰는 업무 목록·일정표·업무 로그를 묶은 권한이고, `files`는 기존 ID를 유지하되 화면 명칭과 책임은 `세부 로그`입니다.
- 고객 권한 선택지와 좌측 메뉴는 프런트의 `frontend/src/accessPermissions.js` 내 `PAGE_CATALOG`에서 함께 파생합니다. 화면을 추가·숨김 처리할 때 `navigation` / `customerSelectable`을 갱신하고, 서버 `apps-script/PermissionAdmin.gs`의 `MH_ACCESS_PAGES`와 양쪽 권한 계약 테스트를 동시에 수정해야 합니다. 이 절차를 통과하지 않은 새 화면은 배포하지 않습니다.
- `content`, `tracking`은 데이터와 API 코드를 삭제하지 않고 현재 메뉴·신규 고객 권한에서 숨깁니다. 고객의 기존 JSON에 남아 있어도 정규화 과정에서 제거되고 서버 직접 조회도 거부됩니다.
- Script Properties: 계정별 비밀번호 HMAC digest만 저장합니다. 비밀번호 원문은 시트·프런트·Git 저장소 어디에도 저장하지 않습니다.
- 기존 권한 시트에 `allowed_pages_json` 열이 없으면 포켓 계정이 권한 관리 화면을 처음 조회할 때 자동으로 추가합니다. 기존 고객 권한의 빈 값은 호환을 위해 전체 페이지 허용으로 해석합니다.
