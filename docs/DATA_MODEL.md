# 데이터 모델

## 핵심 원칙

1. 고객사명·프로젝트명 같은 표시값으로 관계를 연결하지 않고 불변 ID로 연결한다.
2. 한 셀에 프로젝트 전체 JSON을 저장하지 않는다.
3. 웹 입력은 대상 탭의 한 행으로 저장하고 `15_활동로그`에 같은 작업의 이벤트를 추가한다.
4. 일반 삭제는 행 삭제가 아니라 `archived_at`을 기록하는 보관 방식으로 처리한다. 명시적인 전체 초기화만 검증된 전체 원장 백업을 선행하고 물리 삭제하며, 삭제 건수와 실행자는 `15_활동로그`에 남긴다.
5. 고객 화면은 `client_id`, `project_id`, `visibility_code`, 권한 정보를 서버에서 검사한 결과만 반환한다.
6. 사용자·콘텐츠·성과·승인은 서로 독립된 원장으로 관리한다.

## 간트 표시 계약

- `캠페인 스케줄 관리.html`을 시각 기준으로 삼되 업무명 열은 현재 표시된 가장 긴 업무명과 편집 컨트롤을 기준으로 360~620px 사이에서 자동 계산한다. 날짜 열은 24px, 업무 행은 32px로 고정하며 화면이 좁으면 간트 컨테이너에서 수평 스크롤한다.
- 이 값은 화면 표시 전용이며 `planned_start_date`, `due_date`, `schedule_dates_json` 저장 계약에는 영향을 주지 않는다.

## 업무 일정표 표시·상태 계약

- 일정표는 원장의 ISO 날짜를 바꾸지 않고 화면에서만 `월.일`로 줄여 표시한다. 업무명/세부내용/일정 열은 각각 290px/200px/126px이며 전체 표 폭은 1244px을 유지한다.
- 일정표의 상태 순환 조작으로 `DONE`을 선택하면 `progress_percent = 100`을 같은 mutation에 포함한다. 완료 이후 다른 상태로 변경할 때는 사용자가 입력한 진행률을 임의로 되돌리지 않는다.

## 프로젝트 생성 계약

- 현재 UI의 전역 선택 단위는 `clients` 한 행과 대표 `projects` 한 행의 1:1 운영 쌍이다. `프로젝트 추가`는 이 두 행과 생성자의 `project_memberships`를 `create_project` RPC 한 트랜잭션으로 생성한다.
- 생성 가능 주체는 활성 `POCKET_MANAGER / POCKET_EDITOR / EXECUTOR_EDITOR`이며 조직은 `POCKET / NS`로 제한한다. 고객 계정은 생성할 수 없다.
- 생성자 권한은 포켓 `ADMIN`, NS `EDIT`이고 기본 허용 페이지는 `overview / plan / tasks / progress / daily / performance / files`다. `client_view_enabled`는 고객 계정을 별도 배정하기 전까지 `false`다.
- 회사명은 활성 고객사 사이에서 대소문자·앞뒤 공백을 무시해 중복을 거부한다. `mutation_id` 재호출과 동시 생성은 advisory transaction lock으로 직렬화한다.
- 같은 고객사 아래 여러 프로젝트를 추가하는 모델은 아직 UI 선택 계약에 포함하지 않는다. 이를 도입할 때는 회사 선택과 프로젝트 선택을 분리하고 `bootstrapViewModel`의 첫 프로젝트 선택 가정을 먼저 제거해야 한다.

### 견적서 기반 프로젝트 생성

- 포켓·NS 내부 계정은 상단 `견적서 불러오기`에서 PDF, XLSX/XLS/XLSM, CSV, TSV를 읽고 고객사·프로젝트명·기간·견적 항목을 검토한 뒤 `현재 프로젝트에 추가` 또는 `새 프로젝트로 만들기`를 선택한다. PDF는 텍스트 레이어가 있는 문서만 지원하며 스캔 이미지만 있는 PDF는 OCR 대상이 아니다.
- 브라우저 파서는 파일을 서버로 업로드하지 않고 공통 행·열 구조로 변환한다. 열 이름이 다른 문서는 항목명·세부내용·수량·단가·금액 매핑을 사용자가 수정할 수 있다. 엑셀·PDF 라이브러리는 파일을 고른 뒤에만 지연 로드해 첫 화면 로딩에 포함하지 않는다.
- 선택한 견적 항목은 `tasks`의 독립 행으로 만든다. 수량 분할을 켜면 항목 수량만큼 업무를 나누고, 프로젝트 기간 안에서 종료일을 분산한다. 파생 디자인 업무를 켜면 유튜브 썸네일·채널 디자인·블로그 디자인처럼 기준 규칙에 해당하면서 원 견적 세부내용에는 해당 산출물이 없는 경우에만 포켓 담당 업무를 추가한다. `채널 아트·프로필 제작`, `대문·배너·프로필 제작`, `썸네일`처럼 이미 포함된 산출물을 별도 행으로 중복 생성하지 않는다. 가져온 업무의 진행률은 추정하지 않고 항상 0으로 시작한다.
- 원본 파일명·발행일·견적 메타데이터·합계는 `projects.quote_data` JSON 객체에 저장한다. 고객 계정의 `read_task_workspace` 응답에서는 이 객체를 빈 객체로 마스킹하며, 견적 금액은 내부 계정에만 노출한다.
- 새 프로젝트 생성은 `create_project_from_quote`, 기존 프로젝트 추가는 `import_quote_tasks` RPC를 사용한다. 두 RPC 모두 최대 600개 업무를 단일 트랜잭션으로 저장하고, 한 행이라도 검증에 실패하면 프로젝트·견적 메타데이터·업무 전체를 롤백한다. `mutation_id`와 advisory transaction lock으로 재요청 중복도 차단한다.
- 원천 표시는 `source_code = QUOTE_IMPORT`, 파생 업무는 `QUOTE_IMPORT_DERIVED`다. 견적서 가져오기는 Supabase 업무 원장에만 쓰며 Google Sheets 업무 탭에 동시 기록하지 않는다.

## UND 90일 업무 구조

`91_업무템플릿`에는 과거 UND 승인 계획 144개가 별도 보존되어 있고, 현재 `06_업무`의 UND 78개는 이 템플릿이 아니라 기준 캠페인 HTML의 9월 일정입니다. 두 원천을 자동 병합하지 않으며 `sync_und_task_structure`를 실행하면 현재 78건 외에 과거 승인 업무가 다시 추가될 수 있으므로 운영 중 실행하지 않습니다.

캠페인 HTML 이관 행은 `source_code = CAMPAIGN_SCHEDULE_HTML`, `source_task_id = CAMPAIGN_SCHEDULE_V1_{캠페인}_{원본행ID}`로 식별합니다. 원본 매체는 `category_code`, 업무 분야는 내용 기준 `MKT / DSN / VID`, 담당은 `POCKET / NS`, 고객 공개 일정은 `visibility_code = CLIENT`로 저장합니다. 원본의 날짜 경과율은 실제 진행률이 아니므로 `progress_percent = 0`을 유지합니다. HTTPS 링크만 `completion_url`에 넣고 `디자인완료` 같은 비 URL 값은 `remarks`의 `완료링크 원문:`으로 보존합니다. 기준 파일의 예시 이슈 행은 운영 데이터로 이관하지 않으며, 새 이슈·추가요청은 업무 비고가 아닌 Supabase `project_issues`에 독립 저장합니다.

팀 트래커 전용 필드는 다음과 같습니다.

| 필드 | 저장 위치 | 의미 |
|---|---|---|
| `plan_week` | 06_업무, 91_업무템플릿 | 해당 단계 안에서 계획된 주차. 명시적인 `due_date`가 없을 때 프로젝트 `start_date`와 단계 일정으로 마감일을 계산하는 기준 |

일정표·간트의 업무 삭제는 `DELETE`가 아니라 `mutate_task`의 `ARCHIVE`다. 활성 조회에서는 즉시 제외되지만 `tasks.archived_at`, `updated_by_user_id`, `last_mutation_id`, `activity_events`는 남아 복구와 사용자 변경 추적이 가능하다.

UND 운영 업무는 P0/M1/M2/M3 단계와 `plan_week`를 기준으로 `planned_start_date`와 `due_date`를 원장에 명시적으로 저장합니다. 날짜가 없는 구버전 행만 화면에서 프로젝트 착수일과 단계·주차를 기준으로 계산합니다.

업무 `일정표` 화면은 `매체 / 업무 / 세부내용 / 일정 / 기간(일) / 진행률 / 상태 / 담당 / 완료링크 / 비고` 10개 열로 구성합니다. `일정` 셀 안에서 시작일과 종료일을 함께 수정하고, 셀을 벗어날 때 두 경계일과 `schedule_dates_json`을 한 번의 저장 요청으로 동기화합니다. 매체는 그룹 첫 행뿐 아니라 모든 업무 행에 표시하며 담당은 `responsible_org_code`를 현재 프로젝트 고객사명과 조합해 표시합니다. 구버전 행은 시작일~종료일을 연속 구간으로 표시하고, 간트에서 한 번이라도 편집한 행은 `schedule_dates_json`의 실제 선택 날짜만 채웁니다. 선택 날짜의 최솟값·최댓값은 `planned_start_date`·`due_date`에도 동기화하고 기간은 두 경계일을 포함해 화면에서 계산합니다. Apps Script는 Sheets Date 객체를 KST `yyyy-MM-dd`로 정규화해 브라우저 시간대에 따른 하루 밀림을 방지합니다.

일정표 필터는 별도 저장값을 만들지 않고 `06_업무`의 원천 필드로만 계산합니다. 상태는 `status_code`를 `완료 / 진행 / 보류`로 묶고, 업무 카테고리는 `workstream_code`의 `마케팅 / 디자인 / 영상`을 사용합니다. 업무 일정은 월요일~일요일을 한 주로 하여 `지난주 / 이번주 / 다음주` 안에 실제 선택된 간트 날짜가 하나라도 있으면 표시합니다. 간트 미편집 구버전 행만 `planned_start_date`~`due_date` 연속 구간을 사용합니다. 진행률은 필터 판정에 사용하지 않습니다.

일정표 상단의 `완료 / 진행 / 보류` 집계도 같은 상태 필터를 조작합니다. 선택한 상태를 다시 누르면 전체 상태로 돌아가며, 아래 상태 필터와 선택값을 공유합니다. 집계 숫자는 현재 카테고리·일정 범위 안의 상태별 건수를 유지해 다른 상태로 바로 전환할 수 있게 합니다.

일정표와 간트의 기본 행 순서는 `06_업무.sort_order → task_id`로 받은 원장 순서를 기준으로 합니다. 첫 등장 매체 순서를 유지하면서 같은 매체의 업무를 연속 그룹으로 모으고, 그룹 내부에서는 원장 순서를 바꾸지 않습니다. 일정표와 간트는 이 공통 그룹 배열을 함께 사용하므로 두 화면의 표시 순서와 간트 드래그 저장 대상이 일치합니다. 필터·검색 중에는 원장 일부만 보고 순서를 덮지 않도록 이동을 비활성화합니다. 전체 목록에서는 체크한 여러 업무를 원래 상대 순서 그대로 함께 옮길 수 있고, 다른 매체 그룹에 놓으면 이동 업무의 `category_code`도 대상 매체로 한 번에 변경합니다. 드롭 위치는 대상 행 위·아래 선으로 표시하고 가장자리에서는 목록을 자동 스크롤합니다.

`일정표` 날짜축의 끝은 현재 표시 업무 중 가장 늦은 `due_date`로 제한합니다. `간트`는 실제 첫 업무일부터 마지막 업무일까지 연속 날짜축을 만들고, 업무명 열을 제외한 화면의 남은 폭만큼 다음 날짜를 이어 그립니다. 실제 일정이 화면보다 길면 내부 가로 스크롤을 사용합니다.

간트는 참고 HTML의 전체 계층과 스타일 코드(`toolbar`, `panel-head`, `g-hint`, `scroll`, `g-hrow`, `g-months`, `g-days`, `g-grow`, `g-row`, `g-track`, `g-c`, `g-legend`)를 기준으로 사용합니다. 왼쪽 업무명 열은 현재 표시된 가장 긴 이름과 상태·담당·수정 컨트롤 폭을 합산해 360~620px 사이에서 자동 계산하고, 남은 화면 폭은 24px 날짜 셀로 채웁니다. 마지막 실제 일정 뒤에 공간이 남으면 다음 달 날짜까지 연속해서 표시합니다. 빈 셀에서 드래그를 시작하면 가로 날짜 × 세로 업무 범위를 추가하고, 이미 채워진 셀에서 시작하면 같은 범위를 삭제합니다. 중간 날짜만 삭제해도 구멍을 보존하며 드래그 종료 시 변경된 업무를 최대 40건씩 배치 UPDATE합니다. 달력 셀에 포인터를 올리면 해당 업무 행과 날짜 열을 동시에 남색 반투명으로 강조하고 교차 셀에는 외곽선을 표시합니다. 업무명 클릭은 기존 수정 모달을 열고, 읽기 전용 고객 계정에는 페인팅을 허용하지 않습니다. 저장된 `schedule_dates_json`, 파생 경계일과 사용자·변경 시각은 `06_업무`와 `15_활동로그`에 함께 반영합니다. 드래그의 행 번호와 저장 대상 배열은 매체별로 묶인 실제 렌더링 순서를 단일 기준으로 사용하며, 화면 순서가 달라져 다른 업무까지 함께 변경되는 것을 허용하지 않습니다. 기준 HTML에 없던 프로젝트별 필터와 생성·수정 컨트롤은 데이터 운영 기능으로만 유지합니다.

업무 체크박스는 일반 클릭 외에 Shift 범위 선택을 지원합니다. 마지막으로 누른 업무와 현재 업무 사이에서 화면에 보이는 행만 선택·해제하고, 필터 밖에 이미 선택된 업무는 보존합니다. 선택 업무는 상태·담당 일괄 변경, 묶음 이동, 일괄 보관 삭제에 공통으로 사용합니다. 일괄 삭제는 오작동을 막기 위해 같은 버튼을 한 번 더 눌러 확정하며, 각 업무는 `ARCHIVE`로 처리되어 원장과 사용자 로그에서 복구 가능한 이력을 유지합니다.

일정표 헤더의 `업무 추가`는 업무 목록의 생성 폼과 동일한 CREATE API를 사용합니다. 생성 UI 위치만 일정표 안으로 옮기며 신규 업무의 저장 구조와 권한 검사는 변경하지 않습니다.

## 프로젝트 이슈·추가요청

`project_issues`는 일정표 하단의 이슈·추가요청 한 행을 프로젝트별로 저장합니다.

| 필드 | 의미 |
|---|---|
| `issue_date` | 사용자가 지정한 등록일 |
| `kind_text` | 이슈·추가업무 등 자유 구분 |
| `related_task_text` | 관련 업무 표시명. 업무 FK가 아니라 원문을 보존하는 자유 입력 |
| `body_text` | 요청·이슈 본문 |
| `owner_text` | 담당자·담당 조직 자유 입력 |
| `status_code` | `NOT_STARTED / IN_PROGRESS / DONE / ON_HOLD` |
| `completion_url` | 비어 있거나 HTTP(S) 완료 링크 |
| `remarks` | 비고 |
| `visibility_code` | 기본 `CLIENT`; 고객은 읽기만 가능 |
| `created_by_user_id`, `updated_by_user_id` | 생성·마지막 수정 사용자 |
| `row_version`, `archived_at`, `last_mutation_id` | 동시 수정·보관·중복 요청 제어 |

화면의 삭제는 행을 물리 삭제하지 않고 `archived_at`을 기록합니다. 업무 목록과 이슈 목록은 `read_task_workspace` 한 응답으로 읽되 서로 다른 원장을 유지합니다.

## 프로젝트 공통 화면 원칙

프로젝트마다 바뀌는 값은 고객사명, 프로젝트명, 업무·일정·성과 데이터와 공개 범위뿐입니다. 업무 목록, 일정표, 필터, 업무 추가·수정, 로그 같은 화면 프레임과 조작 위치는 프로젝트 ID나 고객사명으로 분기하지 않습니다. 포켓·NS 내부 계정에는 접근 가능한 모든 프로젝트에서 같은 업무 조작 프레임을 제공하고, 각 저장 요청의 실제 쓰기 권한은 Apps Script가 `04_프로젝트권한`을 다시 조회해 최종 검증합니다.

공통 화면은 `좌측 메뉴 / 본문` 두 영역만 사용합니다. 회사 단위 프로젝트 선택은 전역 상단 바의 이름형 탭으로 고정하고, 좌측에는 실행계획·업무·회의록·성과·로그·권한 같은 화면 메뉴만 표시합니다. 회사명과 프로젝트 상태·단계·연결 상태를 좌측에서 중복 표시하지 않습니다.

업무 담당 코드 `CLIENT`의 표시명은 고정 문자열이 아닙니다. 현재 프로젝트의 `client_name`을 bootstrap 프로젝트 셸에서 전달해 UND에서는 `UND`, 무극에서는 `무극`으로 표시합니다. 화면별 API 응답의 축약된 프로젝트 정보는 bootstrap 셸과 병합하며, 프로젝트를 바꿔도 고객사명과 권한·페이지 정보가 사라지지 않게 유지합니다.

프런트의 bootstrap 세션 캐시는 권한·프로젝트 셸 계약이 바뀔 때 버전을 올립니다. 캐시가 남아 있더라도 포켓·NS의 업무 프레임 노출은 프로젝트별 캐시 권한값에 의존하지 않으며, 고객 계정은 계속 읽기 전용입니다.

업무 조회 결과는 화면 로딩 완화를 위해 로그인 사용자와 프로젝트를 키로 `sessionStorage`에 최대 30분 캐시합니다. 캐시는 서버 원장을 대체하지 않고 먼저 그릴 읽기 사본이며, 화면 진입 즉시 최신 `tasks` API를 다시 호출합니다. 저장 성공 시 캐시도 정식 응답값으로 갱신하고 로그아웃 시 삭제합니다.

로컬 캠페인 일정표는 별도 원장을 만들지 않고 `06_업무`에 `schedule_dates_json` 한 열만 추가합니다. 프로젝트를 선택하면 같은 업무 원장을 `일정표 / 간트`로 전환하고, 사용자 작업 이력은 `업무 로그`로 이동합니다. 동일 업무를 단계 카드와 별도 표로 다시 보여주던 구버전 `운영 보드` 화면과 진입 버튼은 중복이라 제거했습니다. 분야 필터는 `workstream_code`, 상태 필터는 `status_code`를 사용합니다. 표의 업무·세부내용·시작일·종료일·진행률·완료링크·비고는 각각 기존 `06_업무` 필드에 직접 대응하고, 기간은 두 날짜를 포함해 화면에서 계산합니다. 전체 진척은 완료 건수 비율이고 개별 진행률은 `progress_percent`가 비어 있으면 0으로 표시합니다. 필터·화면 전환은 화면 상태일 뿐 Google Sheets에 저장하지 않습니다.

`일정표 / 간트 / 업무 로그` 전환 탭은 세 화면에서 같은 위치와 구성으로 유지합니다. 내부 계정이 업무 로그로 이동해도 일정표·간트 탭을 제거하거나 컴포넌트 내부 상태를 폐기하지 않으며, 로그에서 돌아갈 때 직전 일정 보기 모드를 복원합니다. 프로젝트가 바뀌면 다른 프로젝트의 보기 상태가 섞이지 않도록 일정표로 초기화합니다. 고객 계정은 `tasks` 읽기 권한으로 일정표와 간트만 볼 수 있고 내부 감사 화면인 업무 로그 탭은 렌더링하지 않습니다. 이 전환 상태는 브라우저 UI 상태이며 `06_업무`나 `15_활동로그`에 저장하지 않습니다.

상단 회사 탭은 bootstrap의 고객사·프로젝트 권한 목록을 그대로 사용합니다. 현재 운영 탭은 UND·무극·포켓컴퍼니이며, 포켓컴퍼니는 `CLT-POCKET / PRJ-POCKET-INTERNAL-001`의 독립 고객사·프로젝트로 저장합니다. 화면 메뉴는 새 원장을 만들지 않고 `PAGE_CATALOG`, `allowed_pages_json`, 역할 코드로 계산합니다. 회사 전환은 해당 회사의 `project_id`를 선택하고 일정표로 이동하며, URL 해시와 프로젝트별 리소스 캐시 키를 그대로 사용하므로 회사 간 업무·로그·회의록·KPI가 섞이지 않습니다. 포켓컴퍼니 내부 프로젝트는 고객 공개를 끄고 별도 멤버십을 부여하지 않아 기본적으로 포켓 관리자에게만 노출합니다.

업무 탭의 `업무 로그`는 실제 사용자와 매칭된 계정이 웹에서 실행한 `CREATED / UPDATED / ARCHIVED`만 표시합니다. 완료 처리는 상태를 변경한 `UPDATED`에 포함합니다. 현재 `06_업무`와 `entity_id`를 대조해 업무명을 복원하며, 업무명 복원이 불가능한 행, `03_사용자`와 매칭되지 않는 자동화·시스템·마이그레이션 행, 사용자 필드 변경이 없는 `UPDATED` 행은 제외합니다. 내부 ID, 시스템성 이벤트와 원본 감사 정보는 삭제하지 않고 `세부 로그`에서 유지합니다. 업무 로그에 표시하는 변경 필드는 제목·상태·세부내용·시작일·종료일·진행률·완료링크·비고·우선순위·담당·분야·단계·공개범위로 제한합니다. Supabase `activity_events`는 애플리케이션 만료 기간 없이 append-only로 누적하며, 화면은 최신 200건부터 keyset cursor 방식으로 이전 기록을 계속 불러옵니다. 따라서 로그 증가가 최초 화면 속도를 떨어뜨리지 않으면서 전체 과거 이력을 조회할 수 있습니다.

## 데일리 회의록

`19_데일리회의록`은 프로젝트별 일일 회의 기록을 한 행씩 저장합니다. `meeting_date`, `title`, `attendees_text`, `discussion_text`, `decisions_text`, `action_items_text`, `created_by_user_id`, `visibility_code`를 분리하며 수정은 `row_version`, 생성·수정은 `15_활동로그` PREPARE/COMMIT으로 추적합니다. 기본 공개 범위는 `PROJECT_TEAM`이고 포켓 운영자만 고객 공개 또는 포켓 전용으로 변경할 수 있습니다.

## 콘텐츠 발행 집계

업무 화면의 콘텐츠 발행 실적은 수동 카운터나 업무 JSON에 저장하지 않습니다. `08_콘텐츠`에서 다음 조건을 만족하는 행만 업무의 `task_id → phase_code` 관계로 집계합니다.

- `status_code = PUBLISHED`
- 롱폼: `LONG_FORM`, `LONGFORM`, `YOUTUBE_LONG`
- 숏폼: `SHORT_FORM`, `SHORTFORM`, `YOUTUBE_SHORT`, `REELS`
- 인스타그램: `INSTAGRAM`, `FEED`, `INSTAGRAM_FEED`, `CARD_NEWS`
- 네이버 블로그: `NAVER_BLOG`, `BLOG`, `ARTICLE`

단계별 목표는 P0 `2/10/10/10`, M1~M3 각각 `2/10/10/4` 순서로 롱폼/숏폼/인스타그램/블로그를 사용합니다. API는 원천을 `08_콘텐츠:PUBLISHED`로 명시하고 실제값과 목표값을 함께 반환합니다.

## 고객 읽기 전용 경계

공개 미리보기와 고객 계정은 `CLIENT_VIEWER + READ_ONLY`로 고정합니다. 고객은 `visibility_code = CLIENT`인 업무만 조회하며 업무 생성·상태 변경·담당자 변경·메모 저장을 할 수 없습니다.

고객 업무 응답에는 일정, 단계, 분야, 분류, 공개 상태, 세부내용 `description`, `plan_week`, 공개 진행 메모와 `contract_linked` 여부를 포함할 수 있습니다. `plan_note`, 내부 담당자 ID, 검토 조직, 차단 사유와 원천 코드는 제외합니다. 계약 연계 여부가 `true`여도 계약·검수 사유 원문은 노출하지 않습니다.

## 클라이언트 공유 실행계획

`17_실행계획`은 승인본의 버전·기간·목표를 저장하고 `18_실행계획섹션`은 실행 개요부터 미팅 결정사항까지 10개 섹션을 순서대로 저장합니다. 원본 HTML의 스크립트·스타일·SVG 장식은 저장 전에 제거하며, 서버와 브라우저가 본문 HTML을 각각 다시 정제합니다. 공개 행은 `visibility_code = CLIENT`, `source_code = CLIENT_APPROVED_PLAN`, `status_code = PUBLISHED`만 사용합니다. 실행계획은 읽기 전용이며 실제 진행률은 `06_업무`, 발행 실적은 `08_콘텐츠`에서 별도로 계산합니다.

## 내부 실행계획

내부 실행계획도 별도 JSON 셀이나 새 탭을 만들지 않고 `17_실행계획` / `18_실행계획섹션`에 같은 정규화 구조로 저장합니다. 계획 종류는 기존 `source_code`로 구분합니다.

| 계획 종류 | source_code | 계획 공개 범위 | 섹션 공개 범위 |
|---|---|---|---|
| 클라이언트 공유용 | `CLIENT_APPROVED_PLAN` | `CLIENT` | `CLIENT` |
| 내부 실행계획 | `INTERNAL_EXECUTION_PLAN` | `PROJECT_TEAM` | 본문 `PROJECT_TEAM`, 실행팀 부록 `POCKET_ONLY` |

내부 원문을 Git에 커밋하지 않습니다. `scripts/generate-und-internal-plan.mjs`가 로컬 원문을 정제해 gitignored 임시 Apps Script 번들을 만들고, 관리자 마이그레이션으로 원장에 안정적인 ID를 upsert한 뒤 임시 번들은 배포 소스에서 제거했습니다. 고객 역할은 내부 계획을 요청할 수 없고 내부 계획 행 자체도 `mhCanSeeRow_` 공개 범위 검사를 거칩니다.

## 고객사 계정·페이지 권한

- `03_사용자`: 고객 계정 ID를 내부 `@hub.local` 식별자로 정규화하고 표시 이름, `CLIENT_VIEWER`, 활성 상태를 저장합니다.
- `04_프로젝트권한`: 계정과 고객사·프로젝트 연결, `READ_ONLY`, `allowed_pages_json`을 저장합니다. 현재 선택 가능한 허용 페이지 코드는 `overview`, `plan`, `tasks`, `progress`, `daily`, `performance`, `files`입니다. 프로젝트 하위의 `tasks`(업무 목록·일정표·간트·업무 로그), `progress`(진행상황 요약), `daily`(데일리 회의록)는 각각 독립 메뉴 권한입니다. `progress`는 별도 원장을 만들지 않고 고객 공개 업무 투영을 읽으며, `files`는 기존 ID를 유지하되 화면 명칭과 책임은 `세부 로그`입니다.
- 고객 권한 선택지와 좌측 메뉴는 프런트의 `frontend/src/accessPermissions.js` 내 `PAGE_CATALOG`에서 함께 파생합니다. 화면을 추가·숨김 처리할 때 `navigation` / `customerSelectable`을 갱신하고, 서버 `apps-script/PermissionAdmin.gs`의 `MH_ACCESS_PAGES`와 양쪽 권한 계약 테스트를 동시에 수정해야 합니다. 이 절차를 통과하지 않은 새 화면은 배포하지 않습니다.
- `content`, `tracking`은 데이터와 API 코드를 삭제하지 않고 현재 메뉴·신규 고객 권한에서 숨깁니다. 고객의 기존 JSON에 남아 있어도 정규화 과정에서 제거되고 서버 직접 조회도 거부됩니다.
- Script Properties: 계정별 비밀번호 HMAC digest만 저장합니다. 비밀번호 원문은 시트·프런트·Git 저장소 어디에도 저장하지 않습니다.
- 기존 권한 시트에 `allowed_pages_json` 열이 없으면 포켓 계정이 권한 관리 화면을 처음 조회할 때 자동으로 추가합니다. 기존 고객 권한의 빈 값은 호환을 위해 전체 페이지 허용으로 해석합니다.
