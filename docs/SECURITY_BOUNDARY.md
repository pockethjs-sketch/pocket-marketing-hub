# 데모와 운영 데이터의 보안 경계

## 현재 운영 구조

- GitHub Pages 프런트는 공개 API 주소만 알고, Google Sheets 원장에는 직접 접근하지 않는다.
- Apps Script가 접속 코드 로그인, 서명 세션, 사용자·프로젝트 권한, 공개 범위를 서버에서 검증한다.
- 접속 코드 원문과 서명 키는 로컬 비밀 파일과 Apps Script Properties에만 보관한다.
- 고객사는 자기 프로젝트의 `CLIENT` 공개 데이터만 읽을 수 있고 쓰기는 차단된다.
- 운영 API 실패 시 번들 데이터나 다른 고객사 데이터로 대체하지 않고 오류를 표시한다.

## 적용된 원장 경계

1. 계정별 접속 코드와 서명 세션을 사용한다.
2. 모든 요청에서 서버가 역할·고객사·프로젝트 권한을 다시 검사한다.
3. 응답 필드는 역할별 화이트리스트로 구성한다.
4. Google Sheet 원본은 비공개로 유지하고 고객에게 직접 공유하지 않는다.
5. Script Properties에만 세션 서명 키와 외부 API 비밀값을 보관한다.
6. 고객 A가 고객 B의 ID를 요청하면 서버가 403을 반환해야 한다.
7. 로그아웃 또는 만료 세션으로 API 호출이 불가능해야 한다.

## 적용된 쓰기 안전장치

- `record_id` 기반 생성·수정·보관
- `mutation_id`로 중복 요청 방지
- `LockService`로 동시 저장 충돌 방지
- 입력 필드 화이트리스트 검증
- 변경 전후 값, 사용자, 시각을 활동로그에 기록
- 행 삭제 대신 `archived_at` 보관
- 일일 백업 러너의 평문 비밀값은 GitHub Actions Secret에, digest는 Script Properties에 저장한다.
- 백업은 별도 Drive 스프레드시트로 생성하고 `21_백업로그`에서 추적한다. 21개 전체 시트의 SHA-256 manifest 일치를 검증하며 실제 격리 원장 복원 훈련은 후속 운영 과제다.

## 내부 운영 계정 분리

- Pocket: `POCKET_MANAGER`, 조직 `POCKET`, 권한 관리·운영 유지보수 허용
- NS: `EXECUTOR_EDITOR`, 조직 `NS`, 배정 프로젝트 편집만 허용
- 역할 문자열만으로 관리자 권한을 주지 않고 `POCKET_MANAGER + POCKET` 조합을 서버에서 함께 검사한다.

화면에서 메뉴를 감추는 것만으로는 권한 제어가 되지 않는다. 권한 경계는 항상 서버에서 강제한다.

고객 권한 제거는 계정을 삭제하거나 다른 프로젝트 권한을 건드리지 않고 대상 `04_프로젝트권한` 행만 `DISABLED + archived_at`으로 보관한다. 요청의 사용자·프로젝트·멤버십 ID가 같은 활성 행에 일치해야 하며, 변경 직후 고객 읽기 캐시 epoch를 폐기한다.

## 실행계획 원문 경계

- 클라이언트 공유 계획은 `CLIENT_APPROVED_PLAN + CLIENT`, 내부 계획은 `INTERNAL_EXECUTION_PLAN + PROJECT_TEAM`으로 분리한다.
- 내부 실행계획의 실행팀 부록·리스크·계약 경계는 섹션 단위로 `POCKET_ONLY`를 강제한다.
- `CLIENT_VIEWER`의 `planType=INTERNAL` 요청은 메뉴 노출 여부와 무관하게 서버가 403으로 거부한다.
- 내부 HTML 원문과 생성된 Apps Script 데이터 번들은 Git에 커밋하지 않는다. 로컬 생성본은 원장 이관 시에만 임시 배포했으며, 17/18 시트의 계획 2행·섹션 31행을 검증한 뒤 배포 소스에서 제거했다.
