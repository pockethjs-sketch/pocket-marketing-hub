# Google Sheets 연동 현황

## 현재 결론

현재 상태는 **비공개 Google Sheets 원장 / Apps Script API / GitHub Pages 프런트 실연동 및 핵심 저장 검증 완료**입니다.

- 운영 원장은 백업 후 사용자·프로젝트 권한·공개 범위를 정리했습니다.
- UND 팀 트래커의 승인 업무 144건을 `APPROVED_PLAN` 원천으로 복구해 운영 집계와 고객 공개 화면에 반영했습니다. 단계별로 P0 57건 / M1 31건 / M2 28건 / M3 28건이며, 분야별로 마케팅 79건 / 디자인 35건 / 영상 30건입니다.
- 2026-08-25 미팅을 반영한 최신 `UND_90일_실행계획_클라이언트공유용.html`을 `17_실행계획` 1행과 `18_실행계획섹션` 10행으로 구조화했습니다. 화면은 iframe이 아니라 현재 Pocket UI로 렌더링하며 원본 SVG·스타일·스크립트는 포함하지 않습니다.
- Apps Script는 로그인, 서명 세션, 역할·프로젝트 권한, 읽기, create/update/archive, 중복 요청 방지, row version, PREPARE/COMMIT 활동로그를 구현했습니다.
- 현재 로그인 UI는 임시 OFF 상태입니다. 서버가 `CLIENT_VIEWER + READ_ONLY` 공개 미리보기 세션을 1시간 단위로 발급하며, `PRJ-UND-90D-001` 허용 프로젝트와 `CLIENT` 공개 행만 조회되고 쓰기는 계속 차단됩니다.
- 로그인 없는 첫 진입은 `preview_bootstrap`으로 1시간 공개 세션과 고객사·프로젝트·채널을 받고, `preview_overview`를 동시에 실행해 총괄을 병렬로 준비합니다. 첫 화면 뒤에는 `project_snapshot` 한 번으로 실행계획·업무·콘텐츠·성과·자료·활동을 준비합니다.
- 고객사는 조회 전용이며 내부 필드와 원시 활동로그를 받지 않습니다.
- 업무 원장은 승인 계획의 `plan_week`, `plan_note`를 저장합니다. API의 `contract_linked`는 `plan_note` 존재 여부로 파생하며 고객에게는 Boolean만 제공하고 계약·검수 사유 원문은 숨깁니다.
- 착수일은 Pocket 내부 사용자만 업무 화면에서 변경할 수 있고 `02_프로젝트.start_date`에 행 버전 충돌 보호와 함께 저장됩니다. 고객과 실행사는 값만 조회합니다.
- 업무 화면의 발행 실적은 `08_콘텐츠`에서 `PUBLISHED` 상태인 롱폼·숏폼·인스타그램·네이버 블로그를 연결 업무의 단계별로 자동 집계합니다. 수동 발행 카운터는 사용하지 않습니다.
- 데스크톱 탐색은 메인 상단의 단일 버튼으로 `메인 화면 → 현재 고객사 프로젝트 메뉴 → 전체 고객사/프로젝트 → 메인 화면`을 순환합니다. 별도 경계·사이드바 화살표는 없으며, 작은 화면도 같은 단일 버튼으로 통합 서랍을 여닫습니다.
- 운영 빌드는 라이브 실패 시 데모 데이터로 대체하지 않습니다.
- 읽기는 실행 내 메모리 캐시와 180초 서버 캐시를 사용합니다. 85KB를 넘겨 캐시에서 빠지던 `06_업무` 같은 원장은 gzip으로 압축한 뒤 캐시하며, 캐시 키에는 스키마·백엔드 버전이 포함돼 재배포 전 권한값이 남지 않습니다. 저장은 캐시를 우회해 최신 행과 `row_version`을 확인하고 성공 직후 관련 캐시를 폐기합니다.
- 프런트는 첫 화면 뒤 `project_snapshot`을 한 번 호출해 후속 5개 화면 캐시를 구성하고, `프로젝트 + 화면`별 최근 응답을 10분 보관합니다. 스냅샷이 실패하면 즉시, 4초 이상 멈추면 해당 탭의 기존 API로 복귀합니다. 수동 새로고침·저장·프로젝트 변경 시 기존 캐시 세대를 폐기합니다.
- 현재 공개 고객 화면은 같은 프로젝트·필터의 완성된 일반 API 응답을 120초, 실행계획·프로젝트 스냅샷을 300초 재사용합니다. 편집 권한 사용자는 이 응답 캐시를 사용하지 않아 저장 직후 오래된 화면이 반환되지 않습니다.
- API 관리 탭은 직접 수정으로 로그·버전을 우회하지 않도록 보호했습니다.
- Apps Script 권한 승인, Web App 배포, 쓰기 활성화, GitHub Actions API URL 변수 설정을 완료했습니다.
- 로컬 Vite의 React StrictMode가 공개 미리보기 첫 요청을 취소한 뒤 재호출을 막던 상태 가드를 제거했습니다. 개발·운영 모두 취소 후 정상 재시도되며 무한 로딩 대신 성공 화면 또는 명시적 오류 화면으로 전환됩니다.
- 유효한 공개 세션은 같은 탭에서 재사용합니다. `preview_session → bootstrap` 직렬 호출은 `preview_bootstrap`으로 통합했고, 첫 총괄은 `preview_overview`와 병렬 조회합니다. 최소 bootstrap에는 총괄·업무 원문을 포함하지 않으며, 후속 탭은 첫 화면 뒤 스냅샷으로 준비합니다.
- 포켓·NS·UND 세 역할 로그인과 프로젝트 격리, 고객 쓰기 차단을 실제 API로 검증했습니다.
- 업무 생성·동일 mutation 재호출·수정·stale row version 거부·보관을 실제 원장과 활동로그에서 검증했습니다.

## 현재 데이터 경계

| 구분 | 데이터 원천 | 영속 저장 | 상태 |
|---|---|---:|---|
| 운영 웹 화면 | Apps Script 권한 필터 응답 | 해당 없음 | 실연동 |
| Google Sheets 원장 | 사용자 입력·승인 이관 | 예 | 운영 원장 |
| 업무·콘텐츠·자료 생성 | 포켓·NS 웹 입력 | 예 | 원장+활동로그 동시 기록 |
| 고객사 화면 | 본인 프로젝트의 CLIENT 공개 데이터 | 해당 없음 | 읽기 전용 |
| 실행계획 | 17_실행계획 + 18_실행계획섹션 | 예 | 최신 승인본 읽기 전용 |
| 채널 성과 동기화 | 아직 미설정 | 아니요 | 별도 연결 필요 |
| 활동로그 | 웹 mutation PREPARE·COMMIT | 예 | 관리자/실행사 조회 |

## 원장에 준비된 범위

원장은 다음 관계를 불변 ID로 연결하도록 설계돼 있습니다.

`고객사 → 프로젝트 → 업무·콘텐츠 → 승인·성과 → 파일·활동로그`

승인된 UND 업무 144건은 운영 집계에 포함됩니다. 기존 103건에서 144건으로 이관할 때 의미상 동일 업무는 상태·담당자·메모를 보존하고 누락 업무만 추가하도록 마이그레이션을 구성했습니다. 콘텐츠, 승인, 성과, KPI 실적은 운영 입력을 받는 원장입니다. 외부 채널 API는 아직 연결되지 않았습니다.

업무 144건의 구성은 다음과 같습니다.

| 구분 | 건수 |
|---|---:|
| P0 / M1 / M2 / M3 | 57 / 31 / 28 / 28 |
| 마케팅 / 디자인 / 영상 | 79 / 35 / 30 |

업무 API는 프로젝트 `start_date`, 업무 `plan_week`, 명시적인 `due_date`를 반환합니다. 프런트는 저장된 `due_date`를 우선하고 값이 없을 때 `start_date + 단계 + plan_week`로 일정과 D-day를 계산합니다. `plan_note`는 내부 상세에서만 조회되며 고객 화면은 `contract_linked` 여부와 공개 진행 메모만 확인합니다.

세부 탭과 필드 정의는 [데이터 모델](DATA_MODEL.md), 화면별 읽기 구조는 [API 계약](API_CONTRACT.md)을 기준으로 합니다.

## 공개 범위

원장과 API 공개 범위는 `POCKET_ONLY`, `PROJECT_TEAM`, `CLIENT`로 통일했습니다. 기존 `INTERNAL` 값은 `POCKET_ONLY`로 이관했고, 신규 실행사 입력의 기본 공개 범위는 `PROJECT_TEAM`입니다.

권장 기준은 다음 세 단계입니다.

| 코드 | 공개 대상 | 포함 예시 |
|---|---|---|
| `POCKET_ONLY` | 포켓 내부 | 전략, 원가, 위험, 계약 기준, 내부 메모 |
| `PROJECT_TEAM` | 포켓 + 배정 실행사 | 제작 지시, 작업 메모, 실행사 담당 정보 |
| `CLIENT` | 고객사 | 일정, 공개 결과물, 승인 요청, 공개 성과 |

고객 공개는 포켓 검수 후 `CLIENT`로 변경합니다.

## 운영 구조

```text
GitHub Pages 프런트엔드
        ↓ HTTPS
Apps Script API
        ├─ 로그인 세션 확인
        ├─ 사용자·프로젝트 권한 확인
        ├─ 역할별 응답 필드 화이트리스트
        ├─ 입력 검증·동시 저장 제어
        └─ 활동로그 기록
        ↓
비공개 Google Sheets 원장
```

브라우저가 보낸 `role`, `client_id`, `project_id`는 권한 근거로 신뢰하지 않습니다. 서버가 로그인 사용자와 프로젝트 권한표를 기준으로 접근 범위를 다시 계산해야 합니다. 시트 원본은 비공개로 유지하고 고객에게 직접 공유하지 않습니다.

## 읽기 연동 상태

사용자·권한 등록, 공개 범위, 통합 bootstrap, 화면별 지연 조회, 보관행 제외, 역할별 필드 projection, 로딩·오류·재시도·마지막 동기화 표시를 구현했습니다. 활성 고객사·프로젝트는 UND만 남겼고, 역할별 배정 범위를 실제 API로 확인했습니다. 고객용 `CLIENT_VIEWER` 응답은 `CLIENT` 공개 업무만 반환하며 `plan_note`, 내부 설명·담당자·차단 사유를 제거하고 모든 mutation을 차단합니다.

## 쓰기 연동 상태

업무·콘텐츠·자료 CREATE 폼과 서버의 create/update/archive 계약은 연결됐습니다. `LockService`, `row_version`, actor에 바인딩된 `mutation_id`, PREPARE·COMMIT 활동로그, 보관 처리, 저장 성공 후 재조회까지 구현했습니다. 내부 편집자는 업무 행 상세에서 상태·담당자·메모를 수정할 수 있고, 고객과 공개 미리보기는 같은 상세를 읽기 전용으로 사용합니다.

구체적인 저장 규칙은 [저장·연동 원칙](STORAGE_AND_SYNC.md), 인증과 비밀값 기준은 [보안 경계](SECURITY_BOUNDARY.md)를 따릅니다.

## 구현 우선순위

### 완료

- 공개 범위 통일과 참고 데이터 보관
- 사용자·프로젝트 권한 등록
- 서버 인증·고객사 격리·역할별 projection
- 화면별 읽기와 신규등록 UI
- `mutation_id`, `row_version`, `LockService`, 활동로그
- 로딩·오류·재시도·저장 상태

### 완료된 운영 검증

- Apps Script 최초 OAuth 승인과 health `READY`
- 3개 역할 로그인·프로젝트 격리·고객 쓰기 차단
- 신규등록·중복 mutation·stale row version·보관 흐름
- 원장 행과 PREPARE·COMMIT 활동로그 대조
- 접근코드·서명키 회전 및 Script Properties 동기화

### P2 — 성과와 외부 채널

- 유튜브·메타·네이버·구글 데이터 수집
- 원천 성과와 KPI 집계 분리
- 동기화 상태, 마지막 성공 시각, 실패 사유 표시

### P3 — 운영 안정성

- 매일 별도 Drive 폴더에 백업하고 최소 30일 보관
- 실제 복원 훈련
- 저장·동기화 오류 알림
- 권한 격리, 중복 요청, 동시 수정, 보관·복원 자동 테스트

## 운영 연결 완료 판정

다음 조건을 모두 만족하기 전에는 화면에 `Google Sheets 연동 완료`를 표시하지 않습니다.

- 실제 사용자 인증과 프로젝트 권한 검증 성공
- 공개 범위 코드 통일과 고객 공개 데이터 검수 완료
- 화면의 수치가 원장 행으로 역추적 가능
- 웹 입력이 원장 행과 활동로그에 함께 기록됨
- 중복 요청과 동시 수정 테스트 통과
- 고객사 간 데이터 격리 테스트 통과
- 백업 생성과 복원 테스트 통과
