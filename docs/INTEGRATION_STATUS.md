# Google Sheets 연동 현황

## 현재 결론

현재 상태는 **비공개 Google Sheets 원장 / Apps Script API / GitHub Pages 프런트 실연동 및 핵심 저장 검증 완료**입니다.

- 운영 원장은 백업 후 사용자·프로젝트 권한·공개 범위를 정리했습니다.
- UND 팀 트래커의 승인 업무 144건을 `APPROVED_PLAN` 원천으로 복구해 운영 집계와 고객 공개 화면에 반영했습니다. 단계별로 P0 57건 / M1 31건 / M2 28건 / M3 28건이며, 분야별로 마케팅 79건 / 디자인 35건 / 영상 30건입니다.
- 2026-08-25 미팅을 반영한 최신 `UND_90일_실행계획_클라이언트공유용.html`을 `17_실행계획` 1행과 `18_실행계획섹션` 10행으로 구조화했습니다. 화면은 iframe이 아니라 현재 Pocket UI로 렌더링하며 원본 SVG·스타일·스크립트는 포함하지 않습니다.
- 내부 실행계획을 같은 17/18 원장에 설치하고 `CLIENT_SHARE` / `INTERNAL` 선택 API를 연결했습니다. 계획 2행·섹션 31행을 검증했으며 임시 마이그레이션 라우트와 내부 생성 번들은 최종 배포에서 제거했습니다. 본문은 `PROJECT_TEAM`, 실행팀 부록은 `POCKET_ONLY`이고 고객의 내부 계획 요청은 서버에서 거부합니다.
- Apps Script는 로그인, 서명 세션, 역할·프로젝트 권한, 읽기, create/update/archive, 중복 요청 방지, row version, PREPARE/COMMIT 활동로그를 구현했습니다.
- 로그인 UI는 ON 상태이며 공개 미리보기와 익명 업무 쓰기는 모두 OFF입니다. 현재 두 내부 운영 계정은 동일하게 `POCKET_MANAGER` 역할과 UND·무극 프로젝트 `ADMIN` 권한을 사용합니다. 짧은 로그인 아이디는 서버에서 내부 계정 주소로 정규화하며, 비밀번호 원문은 프런트·원장·저장소에 저장하지 않고 Script Properties의 HMAC digest로만 검증합니다.
- 로그인 요청은 서명 세션과 허용 고객사·프로젝트·채널의 최소 `bootstrap`을 한 Apps Script 실행에서 함께 반환합니다. 기존처럼 로그인 후 `bootstrap`을 순차 호출하지 않으며, 구버전 서버의 평면 로그인 응답은 프런트 호환 경로에서만 별도 `bootstrap`을 호출합니다. 비로그인 `preview_bootstrap` 경로는 호환 코드만 남아 있으며 현재 설정에서는 `forbidden`으로 거부됩니다.
- 고객사는 조회 전용이며 내부 필드와 원시 활동로그를 받지 않습니다.
- 업무 원장은 승인 계획의 `plan_week`, `plan_note`를 저장합니다. API의 `contract_linked`는 `plan_note` 존재 여부로 파생하며 고객에게는 Boolean만 제공하고 계약·검수 사유 원문은 숨깁니다.
- 착수일은 Pocket 내부 사용자만 업무 화면에서 변경할 수 있고 `02_프로젝트.start_date`에 행 버전 충돌 보호와 함께 저장됩니다. 고객과 실행사는 값만 조회합니다.
- 업무 화면의 발행 실적은 `08_콘텐츠`에서 `PUBLISHED` 상태인 롱폼·숏폼·인스타그램·네이버 블로그를 연결 업무의 단계별로 자동 집계합니다. 수동 발행 카운터는 사용하지 않습니다.
- 데스크톱 탐색은 메인 상단의 단일 버튼으로 `메인 화면 → 현재 고객사 프로젝트 메뉴 → 전체 고객사/프로젝트 → 메인 화면`을 순환합니다. 별도 경계·사이드바 화살표는 없으며, 작은 화면도 같은 단일 버튼으로 통합 서랍을 여닫습니다.
- 운영 빌드는 라이브 실패 시 데모 데이터로 대체하지 않습니다.
- 읽기는 실행 내 메모리 캐시와 180초 서버 캐시를 사용합니다. 85KB를 넘겨 캐시에서 빠지던 `06_업무` 같은 원장은 gzip으로 압축한 뒤 캐시하며, 캐시 키에는 스키마·백엔드 버전이 포함돼 재배포 전 권한값이 남지 않습니다. 저장은 테이블 캐시를 우회해 최신 행과 `row_version`을 확인하고 대상 원장 캐시는 폐기합니다. 단, `CLIENT_VIEWER`용 완성 응답 캐시는 아직 저장 시 무효화되지 않아 저장 후 재진입에서 이전 값이 최대 5분 노출될 수 있습니다.
- 프런트는 현재 화면의 경량 전용 API를 먼저 호출하고, 그 화면이 사용 가능한 상태가 된 뒤에만 `project_snapshot`으로 후속 화면 캐시를 구성합니다. 스냅샷을 최대 4초 선대기하던 경로는 제거했으며 `프로젝트 + 화면`별 최근 응답은 10분 보관합니다. 수동 새로고침·저장·프로젝트 변경 시 기존 캐시 세대를 폐기합니다.
- Apps Script의 단기 302 리다이렉트가 재사용돼 간헐적 404·무한 대기가 발생하지 않도록 모든 프런트 요청에 고유 `_mh` 값을 부여합니다.
- 고객용 읽기 응답 캐시는 같은 프로젝트·필터의 완성 응답을 120초, 실행계획·프로젝트 스냅샷을 300초 재사용하도록 구현돼 있습니다. 현재는 로그인 필수 운영이므로 익명 `CLIENT_VIEWER` 편집 경로는 사용하지 않습니다.
- API 관리 탭은 직접 수정으로 로그·버전을 우회하지 않도록 보호했습니다.
- Apps Script 권한 승인, Web App 배포, 쓰기 활성화, GitHub Actions API URL 변수 설정을 완료했습니다.
- 로컬 Vite의 React StrictMode가 첫 인증 요청을 취소한 뒤 재호출을 막던 상태 가드를 제거했습니다. 개발·운영 모두 취소 후 정상 재시도되며 무한 로딩 대신 성공 화면 또는 명시적 오류 화면으로 전환됩니다.
- 유효한 로그인 세션은 같은 탭에서 재사용합니다. 최소 bootstrap에는 총괄·업무 원문을 포함하지 않으며, 로그인 직후 현재 탭 데이터부터 우선 조회하고 후속 탭 스냅샷은 백그라운드에서 준비합니다.
- 현재 내부 운영 계정의 로그인과 bootstrap에서 UND·무극 고객사 및 프로젝트 노출을 실제 배포 API로 검증했습니다. 잘못된 비밀번호는 거부되고 공개 미리보기 요청도 차단됩니다.
- 무극 프로젝트는 공개 원본 Google Sheet의 `무극 캠페인 일정표`를 2026-08-31 기준으로 다시 대조했습니다. 기존 안정 ID 20건을 중복 생성하지 않고 시작일·종료일·상태·세부내용으로 갱신했으며, 현재 완료 5건 / 진행 15건 / 날짜 누락 0건입니다. 원본의 진행률은 실제 작업률이 아니라 오늘 날짜 기준 일정 경과율이므로 상태 판정에는 사용하지 않고 진행 메모에만 보조 정보로 남깁니다. 모든 변경은 일반 mutation과 `15_활동로그` PREPARE/COMMIT 경로를 통과했습니다.
- 업무 생성·동일 mutation 재호출·수정·stale row version 거부·보관을 실제 원장과 활동로그에서 검증했습니다.
- 성과 탭에서 프로젝트별 KPI 정의를 생성·수정·보관할 수 있습니다. 목표값·단위·측정주기·채널·고객 공개 여부는 `11_KPI정의`에 저장되며, 고객 계정은 조회만 가능합니다. 무극 프로젝트에서 생성→수정→보관 흐름과 보관 후 조회 제외를 실제 배포 API로 검증했습니다.
- 업무 화면은 `업무 목록 / 표·일정 / 업무 로그`로 구성합니다. 표·일정은 `업무 / 세부내용 / 시작일 / 종료일 / 기간(일) / 진행률 / 상태 / 완료링크 / 비고`와 일 단위 간트를 함께 표시합니다. 기간은 날짜에서 자동 계산하며 나머지는 `06_업무`에 분리 저장합니다. 로그는 내부 사용자가 탭을 열 때만 `15_활동로그`의 확정된 TASK 이벤트를 조회합니다.
- 포켓 계정 전용 `권한 관리` 화면을 추가했습니다. 고객사 로그인 계정을 생성·비활성화하고 프로젝트와 허용 페이지를 지정할 수 있습니다. 계정은 `03_사용자`, 접근 범위는 `04_프로젝트권한.allowed_pages_json`, 비밀번호는 Script Properties의 HMAC digest로 분리 저장합니다. 고객 화면의 메뉴 숨김과 Apps Script의 페이지별 서버 차단을 함께 적용했습니다.
- 권한 관리 백엔드는 `2026-08-27-permission-admin-v20`으로 운영 Web App에 배포했고 health `READY`, 쓰기 활성화를 확인했습니다. 운영 데이터에 임의 고객 계정을 만들지는 않았으며, 실제 첫 계정 생성은 포켓 계정의 권한 관리 화면에서 수행합니다.
- `성과 추적` 화면을 별도로 추가했습니다. `12_성과일별`을 기준으로 노출→반응→클릭→문의 병목, 채널별 비용·문의 기여와 일별 추이를 표시합니다. 별도 JSON이나 프런트 임시 데이터는 저장하지 않습니다.
- 최초 구현이 여러 원장을 한 요청에서 다시 읽어 30초 이상 지연된 문제를 제거했습니다. 성과 추적을 프로젝트 스냅샷에서 분리하고 일별 성과 원장만 읽도록 경량화한 백엔드 `2026-08-27-outcome-tracking-v22`를 운영 Web App에 배포했습니다. 인증된 실제 요청은 약 3초에 정상 응답했으며 현재 UND·무극의 `12_성과일별` 행은 모두 0건입니다.
- 2026-08-31 첫 로딩 진단에서 로그인→bootstrap 2회 순차 Apps Script 실행과 업무 탭의 스냅샷 최대 4초 선대기를 병목으로 확인했습니다. 로그인·bootstrap·첫 총괄/업무 데이터를 한 실행으로 묶고 현재 화면을 우선 표시하도록 구현한 백엔드 식별자는 `2026-08-31-fast-startup-v24`입니다.
- 2026-08-31 무극 일정 동기화에서 Sheets 날짜 셀이 Date 객체로 반환될 때 unrelated 업무 수정까지 `invalid_date`로 거부되던 검증을 수정했습니다. 읽기 응답과 저장값은 KST `yyyy-MM-dd`로 정규화하며 운영 백엔드는 `2026-08-31-muguk-schedule-v25`입니다.
- 업무 바로 아래에 `데일리 회의록` 화면을 추가했습니다. 날짜·참석자·회의 내용·결정사항·후속업무·작성자·공개범위를 `19_데일리회의록` 15개 열에 분리 저장하며 수정 시 행 버전 충돌 보호와 활동로그를 사용합니다. 운영 시트 생성과 빈 목록 조회를 검증했고 백엔드 `2026-08-31-daily-meetings-v26`은 `READY`, 쓰기 활성 상태입니다.
- `06_업무`에 `progress_percent`, `completion_url`, `remarks`를 추가하고 기존 완료·미착수 148건의 진행률을 초기화했습니다. 무극 20건은 원본 진행률 전부, HTTPS 완료링크 3건, 비고 10건을 기존 ID와 활동로그를 유지해 이관했습니다. 운영 백엔드는 `2026-08-31-task-table-v27`입니다.

## 원장에 준비된 범위

원장은 다음 관계를 불변 ID로 연결하도록 설계돼 있습니다.

`고객사 → 프로젝트 → 업무·콘텐츠 → 승인·성과 → 파일·활동로그`

승인된 UND 업무 144건은 운영 집계에 포함됩니다. 기존 103건에서 144건으로 이관할 때 의미상 동일 업무는 상태·담당자·메모를 보존하고 누락 업무만 추가하도록 마이그레이션을 구성했습니다. 콘텐츠, 승인, 성과, KPI 실적은 운영 입력을 받는 원장입니다. 외부 채널 API는 아직 연결되지 않았습니다.

업무 144건의 구성은 다음과 같습니다.

| 구분 | 건수 |
|---|---:|
| P0 / M1 / M2 / M3 | 57 / 31 / 28 / 28 |
| 마케팅 / 디자인 / 영상 | 79 / 35 / 30 |

업무 API는 프로젝트 `start_date`, 업무 `plan_week`, 명시적인 `due_date`를 반환합니다. 프런트는 저장된 `due_date`를 우선하고 값이 없을 때 `start_date + 단계 + plan_week`로 일정과 D-day를 계산합니다. `plan_note`는 내부 상세에서만 조회되며 고객 화면은 `contract_linked` 여부와 공개 진행 메모만 확인합니다.

세부 탭과 필드 정의는 [데이터 모델](DATA_MODEL.md), 화면별 읽기 구조는 [API 계약](API_CONTRACT.md)을 기준으로 합니다.

## 공개 범위

원장과 API 공개 범위는 `POCKET_ONLY`, `PROJECT_TEAM`, `CLIENT`로 통일했습니다. 기존 `INTERNAL` 값은 `POCKET_ONLY`로 이관했고, 신규 실행사 입력의 기본 공개 범위는 `PROJECT_TEAM`입니다.

권장 기준은 다음 세 단계입니다.

| 코드 | 공개 대상 | 포함 예시 |
|---|---|---|
| `POCKET_ONLY` | 포켓 내부 | 전략, 원가, 위험, 계약 기준, 내부 메모 |
| `PROJECT_TEAM` | 포켓 + 배정 실행사 | 제작 지시, 작업 메모, 실행사 담당 정보 |
| `CLIENT` | 고객사 | 일정, 공개 결과물, 승인 요청, 공개 성과 |

고객 공개는 포켓 검수 후 `CLIENT`로 변경합니다.

## 운영 구조

```text
GitHub Pages 프런트엔드
        ↓ HTTPS
Apps Script API
        ├─ 로그인 세션 확인
        ├─ 사용자·프로젝트 권한 확인
        ├─ 역할별 응답 필드 화이트리스트
        ├─ 입력 검증·동시 저장 제어
        └─ 활동로그 기록
        ↓
비공개 Google Sheets 원장
```

브라우저가 보낸 `role`, `client_id`, `project_id`는 권한 근거로 신뢰하지 않습니다. 서버가 로그인 사용자와 프로젝트 권한표를 기준으로 접근 범위를 다시 계산해야 합니다. 시트 원본은 비공개로 유지하고 고객에게 직접 공유하지 않습니다.

## 읽기 연동 상태

사용자·권한 등록, 공개 범위, 통합 bootstrap, 화면별 지연 조회, 보관행 제외, 역할별 필드 projection, 로딩·오류·재시도·마지막 동기화 표시를 구현했습니다. 활성 고객사·프로젝트는 UND와 무극이며, 내부 운영 계정에서 두 프로젝트 접근을 실제 API로 확인했습니다. 고객용 `CLIENT_VIEWER` projection은 코드상 유지되지만 현재 공개 세션 발급이 꺼져 있어 로그인 없이 접근할 수 없습니다.

## 쓰기 연동 상태

업무·콘텐츠·자료와 KPI 정의의 CREATE 폼 및 서버 create/update/archive 계약은 연결됐습니다. `LockService`, `row_version`, actor에 바인딩된 `mutation_id`, PREPARE·COMMIT 활동로그, 보관 처리를 구현했습니다. 업무 UPDATE는 클릭 즉시 화면 캐시를 변경하고 서버가 반환한 최신 행과 `row_version`으로 확정하며, 실패하면 이전 상태로 롤백합니다. 콘텐츠·자료 CREATE, KPI 정의 변경과 프로젝트 착수일 UPDATE는 저장 성공 후 화면 캐시를 다시 읽습니다. 모든 쓰기는 로그인 세션과 서버 권한 검사를 통과해야 합니다.

### 2026-08-26 전면 저장 감사

운영 데이터를 추가하지 않는 읽기 전용 점검으로 현재 배포와 원장을 대조했습니다.

- 운영 API: `READY`, `writesEnabled=true`, backend `2026-08-26-login-alias-v17`, schema `2026-08-26-v3`
- `06_업무`: 144행, 업무 ID 중복 0건, 필수 필드·`row_version` 누락 0건
- 최근 실저장 확인: `TSK-UND-P0-MKT-12`가 2026-08-26 16:26:25에 `IN_PROGRESS`, `row_version=9`로 저장되고 1초 뒤 `15_활동로그`에 `TASK UPDATED`가 기록됨
- `03_사용자` 첫 헤더가 `1열`로 변형돼 토큰의 `user_id`가 비던 문제를 `user_id`로 복구했고, 두 내부 계정의 로그인과 bootstrap을 재검증함
- 프런트 API·탐색·배포 테스트 22건 및 Apps Script 정적 인증 검사 통과

| 화면 기능 | 대상 원장 | 현재 저장 상태 |
|---|---|---|
| 업무 생성 | `06_업무` | 저장 연결됨; 생성 응답 유실 후 재시도 시 중복 생성 방지 보완 필요 |
| 업무 상태·제목·메모·담당 조직·마감·우선순위 수정 | `06_업무` | 저장 연결됨; 담당 조직은 포켓·NS·UND 3개 코드로 저장 |
| 프로젝트 착수일 | `02_프로젝트` | 내부 역할 전용 UPDATE 연결됨 |
| 콘텐츠 등록 | `08_콘텐츠` | 인증된 내부 계정 CREATE 연결됨 |
| 자료 링크 등록 | `14_파일링크` | 인증된 내부 계정 CREATE 연결됨 |
| 실행계획·성과 | `17_실행계획`·`18_실행계획섹션`·`11_KPI정의`·`12_성과일별`·`13_KPI실적` | 실행계획과 실적은 조회 전용, KPI 정의는 내부 계정 생성·수정·보관 연결됨 |
| 변경 이력 | `15_활동로그` | 웹 mutation마다 PREPARE·COMMIT 기록; 업무 탭에서 COMMIT 이력 조회 |

감사에서 확인된 미해결 항목은 다음과 같습니다.

- 업무 완료 체크가 `NOT_STARTED → DONE`, `DONE → NOT_STARTED`를 요청하지만 서버 상태 전이 규칙은 두 전이를 거부합니다.
- 공개 업무 저장 응답은 `description`, `assignee_user_id`를 제거해 저장 직후 화면에서 메모·담당자가 빈 값처럼 보이거나 다음 저장에서 덮일 수 있습니다. 현재 익명 공개 쓰기는 꺼져 있지만 고객 계정 쓰기를 다시 열 때 선행 보완이 필요합니다.
- 고객용 읽기 응답 캐시가 mutation 성공 시 무효화되지 않아 향후 고객 쓰기를 열면 저장 후 이전 값이 최대 5분 재노출될 수 있습니다.
- 화면 계산용 마감일이 다른 필드 저장 시 실제 `due_date`로 기록될 수 있고, 완료 시 `completed_at`은 자동 기록되지 않습니다.
- 동일 `mutation_id` 재호출은 중복을 막지만 응답 유실 뒤 사용자가 신규등록을 다시 누르면 새 ID가 발급돼 중복 행이 생길 수 있습니다.
- Sheet 직접 정렬·삽입과 저장이 겹치면 저장 대상 행이 어긋날 수 있습니다. 행 UPDATE 자체는 한 번의 `setValues`로 묶고 기존 수식 문자열을 보존하도록 보완했습니다.
- mutation 멱등성을 `15_활동로그` 전체 스캔에 의존해 로그가 커질수록 쓰기가 느려지며, PREPARE만 남은 거래를 운영 화면에서 확인할 수 없습니다.
- 업무 조회 상한은 200건이며 콘텐츠·자료도 다음 페이지를 불러오는 화면이 없습니다.
- 자동 일일 백업·별도 보관·실제 복원 훈련은 아직 구현되지 않았습니다.

이 항목들이 해결되기 전까지 저장 상태는 `기본 저장 동작 확인 / 운영 안정화 필요`로 판정합니다.

구체적인 저장 규칙은 [저장·연동 원칙](STORAGE_AND_SYNC.md), 인증과 비밀값 기준은 [보안 경계](SECURITY_BOUNDARY.md)를 따릅니다.
